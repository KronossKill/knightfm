DEPENDENCY UPDATE PROTOCOL (mandatory before delivery)
Before delivering a new version, the AI must ensure that all dependencies are
at their latest stable versions. This protocol is mandatory and must be
executed after the integrity verification and before packaging.

Step 1 — Inventory current dependencies
Backend: read requirements.txt, pyproject.toml, Pipfile, or equivalent.
List every Python package and its current version.

Frontend: read package.json, package-lock.json, yarn.lock, or
equivalent. List every npm package and its current version.

Infrastructure: read Dockerfile, docker-compose.yml, CI configs. List
base images and tool versions.

Tools: read .tool-versions, .nvmrc, .python-version, or equivalent.

Step 2 — Query latest stable versions
For each Python package: query PyPI for the latest stable version.

For each npm package: query npm registry for the latest stable version.

For base images: query Docker Hub or registry for the latest stable tag.

For runtimes: query official release pages for the latest LTS/stable.

Do not use alpha, beta, rc, or pre-release versions unless explicitly
justified and documented.

Step 3 — Detect outdated dependencies
Compare current vs latest stable.

Classify each as: up-to-date, patch behind, minor behind, major behind.

Detect deprecated packages and recommend replacements.

Detect packages with known vulnerabilities (query CVE databases or
safety, pip-audit, npm audit).

Step 4 — Plan the update
For patch and minor updates: apply directly.

For major updates: evaluate breaking changes, document migration steps.

For deprecated packages: propose replacement with justification.

For vulnerable packages: prioritize update.

Document every planned change in /docs/DEPENDENCY_REPORTS/.

Step 5 — Apply updates
Backend: update requirements.txt or equivalent with new versions.

Frontend: update package.json with new versions.

Infrastructure: update base image tags and tool versions.

Regenerate lock files (pip-compile, npm install, poetry lock).

Update .tool-versions, .nvmrc, .python-version if applicable.

Step 6 — Verify compatibility
Run all tests: unit, integration, E2E, property-based.

Confirm all tests PASS.

Run linters and type checkers.

Run security scans.

If any test fails, ABORT the delivery, revert the problematic update, and
document the reason in /docs/DEPENDENCY_REPORTS/.

Step 7 — Generate the Dependency Report
Produce /docs/DEPENDENCY_REPORTS/DEPENDENCY_YYYYMMDD_HHMMSS_UTC.md with:

Timestamp (UTC).

Python packages: current → target → status.

npm packages: current → target → status.

Base images: current → target → status.

Runtimes: current → target → status.

Vulnerabilities detected and resolved.

Breaking changes handled and migrations applied.

Tests status (PASS/FAIL).

Overall status (PASS/FAIL).

Step 8 — Update the changelog
Append an entry to /docs/CHANGELOG.md under "Dependencies" with:

Each updated package and its version change.

Reason for the update.

Any breaking change and its migration.

Link to the Dependency Report.

VERIFICATION PROTOCOL (mandatory before any delivery)
Before delivering a new version, the AI must execute the following verification
protocol in order. Every step must PASS. If any step fails, the AI must fix the
issue and re-run the entire protocol.

Step 1 — Load the last backup
Locate the most recent backup in /backups/.

Read its BACKUP_MANIFEST.json.

Confirm the backup's SHA-256 hash matches the stored hash.

Verify Windows compatibility flags and dependency versions snapshot.

Step 2 — Inventory the current project
List every file in the current project.

Compute the current file count and total size.

Compute SHA-256 for every file.

Verify no file path exceeds Windows long-path limits.

Step 3 — Compare against the backup
Detect added files, removed files, modified files, unchanged files.

Step 4 — Validate removed files
For every removed file, require an explicit justification in
/docs/CHANGELOG.md.

If a removed file has no justification, ABORT the delivery and restore it.

Deprecated files must be moved to /docs/archive/, never deleted.

Step 5 — Validate modified files
For every modified file, require an entry in /docs/CHANGELOG.md with:
path, reason, before/after hash, timestamp (UTC), related phase or task.

If a modified file has no changelog entry, ABORT and add the entry.

Step 6 — Validate added files
For every added file, require an entry in /docs/CHANGELOG.md with:
path, reason, timestamp (UTC), related phase or task.

If an added file has no changelog entry, ABORT and add the entry.

Step 7 — Validate against the master specification
Cross-check every requirement in /docs/MASTER_SPECIFICATION.md.

Confirm each requirement is present in /docs/TRACEABILITY_MATRIX.md.

Confirm each requirement maps to code, test, config, and audit.

If any requirement is missing or unmapped, ABORT and fix.

Step 8 — Validate decisions
Confirm every decision in /docs/decisions/ is still respected.

If a new decision replaces an old one, require an explicit supersession entry
in /docs/CHANGELOG.md and in the new decision file.

Old decisions are archived, never deleted.

Step 9 — Validate tests
Run all tests: unit, integration, E2E, property-based, load, security.

Confirm all tests PASS.

Confirm coverage targets are met.

If any test fails, ABORT and fix.

Step 10 — Validate invariants
Cross-check every invariant in the master specification.

Confirm each invariant is enforced by code and covered by tests.

If any invariant is weakened or missing, ABORT and fix.

Step 11 — Execute Dependency Update Protocol
Execute all 8 steps of the Dependency Update Protocol.

Confirm all dependencies are at latest stable versions.

Confirm no vulnerabilities remain unaddressed.

Confirm all tests still PASS after updates.

If any step fails, ABORT and fix.

RESTORATION PROTOCOL
If any verification step fails, or if the user reports missing information,
execute the restoration protocol:

Step 1 — Diagnose
Identify what is missing, broken, or inconsistent.

Cross-check against the last known good backup.

Step 2 — Isolate
Create a working copy of the current state.

Do not modify the current state yet.

Step 3 — Restore specific files
Restore only the affected files from the backup.

Preserve any newer changes in unaffected files.

Use Windows-safe extraction: Expand-Archive or 7-Zip.

Step 4 — Re-run verification
Re-execute the full Verification Protocol, including Dependency Update
Protocol and Windows Compatibility.

Confirm all steps PASS.

Step 5 — Log the restoration
Append an entry to /docs/BACKUP_LOG.md with:

Timestamp (UTC), reason, files restored, before/after hashes,
verification result, dependency status, Windows compatibility result.

Step 6 — Notify the user
Report in Spanish what was restored and why.

Provide the exact Windows commands to verify the restoration locally.

Troubleshooting
PowerShell won't run scripts
powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
Port already in use
powershell
netstat -ano | findstr :8000
Stop-Process -Id <PID> -Force
Long path errors
Enable Long Paths:

Open gpedit.msc (Windows Pro) or registry.

Navigate to Computer Configuration > Administrative Templates > System > Filesystem.

Enable "Enable Win32 long paths".
Or use a short project root: C:\knightfm\.

Python venv activation fails
powershell
# PowerShell
.\venv\Scripts\Activate.ps1
# CMD
venv\Scripts\activate.bat
Node scripts with env vars
Use cross-env in package.json instead of export VAR=...:

json
"scripts": {
  "dev": "cross-env NODE_ENV=development vite"
}
Docker Desktop not starting
Ensure WSL2 is installed and updated: wsl --update.

Restart Docker Desktop.

Fallback: run backend and frontend manually (see Manual setup).

Antivirus blocking scripts
Add the project folder to antivirus exclusions.

Prefer Set-ExecutionPolicy -Scope Process for one-off runs.

1. **Abre una conversación nueva** con la IA de tu elección (ChatGPT GPT-4/4o, Claude Sonnet/Opus, Gemini 2.5 Pro, OpenCode con modelo local, etc.).
2. **Adjunta** el Master Specification v2.2 de Knight FM.
3. **Adjunta** el proyecto actual (ZIP, repositorio, o archivos sueltos).
4. **Pega el prompt completo** desde el bloque de código de arriba.
5. **Envía**.
6. La IA inicializará el proyecto con todos los artefactos de continuidad, incluyendo `WINDOWS_SETUP.md`, `DEPLOY_WINDOWS.ps1`, `DEPLOY_WINDOWS.bat`, `.gitattributes`, y ejecutará el primer **Dependency Update Protocol** para establecer la línea base de versiones.
7. A partir de ahí, cada backup, verificación y entrega incluirá explícitamente:
   - Chequeo de compatibilidad con Windows.
   - Actualización de todas las dependencias a la última versión estable.
   - Reporte de dependencias (`DEPENDENCY_REPORT.md`).
8. Si el contexto se agota, la IA emitirá `READY_TO_CONTINUE_FROM_PHASE_N`, y tú solo escribirás `CONTINUAR`.
